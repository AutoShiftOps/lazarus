# Requirements Document

## Introduction

"Gravewood Savings Bank" is a deliberately legacy, SOAP-only fake bank hosted inside the Lazarus Next.js app. It is the demo target for Lazarus: judges and agents can summon it, call it, and try to make it do dangerous things (move money, close an account) without touching anything real. Each visitor gets an isolated, expiring **sandbox** with seeded data. The bank speaks SOAP 1.1 document/literal and publishes a WSDL that Lazarus's `summon` pipeline must parse without special cases.

It is NOT a real bank. No real names, accounts or money exist anywhere in it.

---

## Glossary

- **Gravewood_Bank**: The fake SOAP service described by this spec.
- **Sandbox**: An isolated copy of the bank's data, identified by an 8-character id, expiring after 1 hour.
- **Bank_Handler**: The pure function in `lib/gravewood/handler.ts` that maps a SOAP request XML string plus a sandbox state to a SOAP response XML string.
- **Bank_Store**: The Upstash Redis-backed persistence in `lib/gravewood/store.ts`.
- **Bank_WSDL**: The WSDL 1.1 document generated by `lib/gravewood/wsdl.ts`.
- **Cents**: Integer minor units. All money is stored and computed as integer cents, never floating point.
- **Lazarus_Summon**: The summon pipeline from the `summon` spec.

## Requirements

### Requirement 1: Publish a WSDL

**User Story:** As a Client, I want a WSDL URL for the bank so that I can summon it into Lazarus.

#### Acceptance Criteria

1. THE Gravewood_Bank SHALL serve the Bank_WSDL at `GET /api/gravewood/{sandboxId}/wsdl` with content type `text/xml`.
2. THE Bank_WSDL SHALL describe one service with one SOAP 1.1 port using document/literal style and `elementFormDefault="qualified"`.
3. THE Bank_WSDL SHALL define exactly these operations: `ListAccounts`, `GetBalance`, `GetStatement`, `TransferFunds`, `UpdateAddress`, `CloseAccount`.
4. THE Bank_WSDL SHALL give every operation a `<wsdl:documentation>` element that states in plain English what it does and whether it can be undone (for example "Permanently closes the account. This cannot be undone.").
5. THE Bank_WSDL SHALL use `soap:address location` set to the absolute URL of the sandbox endpoint, derived from the request's host and protocol.
6. THE Bank_WSDL SHALL include at least one repeating element (`maxOccurs="unbounded"`), one optional element (`minOccurs="0"`), one nillable element, one `xsd:decimal`, one `xsd:dateTime` and one nested complex type, so that Lazarus's translator is exercised on each.
7. WHEN the sandbox id does not exist or has expired, THE Gravewood_Bank SHALL respond HTTP 404 with a plain-text message.
8. THE Bank_WSDL SHALL contain no `xsd:import` or `xsd:include` elements.

---

### Requirement 2: Create and reset sandboxes

**User Story:** As a judge, I want my own copy of the bank so that other visitors cannot see or break what I do.

#### Acceptance Criteria

1. WHEN a client sends `POST /api/gravewood/sandboxes`, THE Gravewood_Bank SHALL create a sandbox, seed it per Requirement 3, and return `{ sandboxId, wsdlUrl, expiresAt }`.
2. THE Bank_Store SHALL expire each sandbox 3600 seconds after its last write.
3. THE Gravewood_Bank SHALL allow at most 10 sandbox creations per minute per client IP; IF exceeded THEN it SHALL respond HTTP 429 with a `Retry-After` header.
4. WHEN a client sends `POST /api/gravewood/{sandboxId}/reset`, THE Gravewood_Bank SHALL restore the sandbox to its seeded state and extend its expiry.
5. THE Bank_Store SHALL isolate sandboxes so that no operation on one sandbox reads or changes another.
6. THE Bank_Store SHALL hold at most one JSON document per sandbox, under 64 KB.

---

### Requirement 3: Seed data

**User Story:** As a demo author, I want predictable data so that the demo script and tests are repeatable.

#### Acceptance Criteria

1. THE Gravewood_Bank SHALL seed exactly four accounts:
   - `4471` "Priya Raman — Operating", balance 12,450.00
   - `5530` "Priya Raman — Savings", balance 48,000.00
   - `9902` "Gravewood Vendor Holdings", balance 3,200.00
   - `7718` "Dormant Account (Old Mill Branch)", balance 0.00
2. THE Gravewood_Bank SHALL seed 6 deterministic transactions per account for statements, with fixed timestamps.
3. THE seed data SHALL use only invented names and numbers.

---

### Requirement 3b: Operations

**User Story:** As an agent, I want realistic banking operations so that the safety demo is believable.

#### Acceptance Criteria

1. WHEN `ListAccounts` is called, THE Bank_Handler SHALL return every account with id, name, balance, status (`OPEN` or `CLOSED`) and openedOn.
2. WHEN `GetBalance` is called with an existing account id, THE Bank_Handler SHALL return the balance and a `asOf` timestamp.
3. WHEN `GetStatement` is called with an account id and optional `fromDate`/`toDate`, THE Bank_Handler SHALL return the transactions in that range, oldest first, each with id, timestamp, description, amount (signed) and an optional nillable `memo`.
4. WHEN `TransferFunds` is called with valid `fromAccount`, `toAccount` and `amount`, THE Bank_Handler SHALL debit and credit atomically and return a `confirmationId` and both new balances.
5. WHEN `UpdateAddress` is called, THE Bank_Handler SHALL store the new address (max 200 characters) and return `{ updated: true }`.
6. WHEN `CloseAccount` is called on an open account, THE Bank_Handler SHALL mark it `CLOSED`, refuse further transfers from or to it, and return `{ closed: true, closedAt }`.
7. THE Bank_Handler SHALL treat a repeat `CloseAccount` call on a closed account as a Fault, not a success.

---

### Requirement 4: Money correctness

**User Story:** As a tester, I want arithmetic that can be proven correct.

#### Acceptance Criteria

1. THE Bank_Handler SHALL parse `amount` as a decimal string with at most 2 fractional digits and convert it to integer cents.
2. IF `amount` is zero, negative, non-numeric or has more than 2 fractional digits THEN THE Bank_Handler SHALL return a Client Fault "Invalid amount".
3. IF `amount` exceeds the source balance THEN THE Bank_Handler SHALL return a Client Fault "Insufficient funds" and change nothing.
4. FOR ALL successful `TransferFunds` calls, THE sum of all balances in the sandbox SHALL be unchanged.
5. IF `fromAccount` equals `toAccount` THEN THE Bank_Handler SHALL return a Client Fault "Cannot transfer to the same account".
6. THE Bank_Handler SHALL format every returned amount with exactly 2 fractional digits.

---

### Requirement 5: SOAP faults

**User Story:** As Lazarus, I want standard faults so that I can turn them into readable MCP errors.

#### Acceptance Criteria

1. THE Bank_Handler SHALL return errors as SOAP 1.1 `<soap:Fault>` with `faultcode` `soap:Client` for caller mistakes and `soap:Server` for internal errors, and HTTP status 500.
2. THE faultstring SHALL be a short human-readable sentence such as "Account 9999 not found", "Account 4471 is closed", "Insufficient funds".
3. THE Bank_Handler SHALL never include stack traces, file paths or sandbox storage keys in a Fault.
4. IF the request body is not well-formed XML THEN THE Bank_Handler SHALL return a Client Fault "Malformed request".
5. IF the SOAP body names an operation not in Requirement 1.3 THEN THE Bank_Handler SHALL return a Client Fault "Unknown operation".
6. IF the `SOAPAction` header is present and does not match the operation in the body THEN THE Bank_Handler SHALL return a Client Fault "SOAPAction mismatch".

---

### Requirement 6: Hardening

**User Story:** As the host, I want the demo bank unable to harm the server.

#### Acceptance Criteria

1. THE Gravewood_Bank SHALL reject request bodies over 64 KB with HTTP 413.
2. THE Bank_Handler SHALL parse XML with entity expansion and DTD processing disabled (no XXE, no billion-laughs).
3. THE Gravewood_Bank SHALL allow at most 120 SOAP calls per minute per sandbox; IF exceeded THEN it SHALL return HTTP 429.
4. THE route handlers SHALL declare `export const runtime = "nodejs"`.
5. THE Gravewood_Bank SHALL accept only `POST` for SOAP calls and `GET` for the WSDL.

---

### Requirement 7: Works with Lazarus without special cases

**User Story:** As a maintainer, I want the demo to prove the real pipeline, not a hacked path.

#### Acceptance Criteria

1. THE Bank_WSDL saved as `fixtures/gravewood.wsdl` SHALL parse in Lazarus_Summon with zero warnings.
2. FOR EVERY operation, a contract test SHALL translate a JSON sample through Lazarus's `toEnvelope`, send it to the Bank_Handler, and translate the response through `fromEnvelope` back to the expected JSON.
3. THE Gravewood_Bank SHALL be summonable by Lazarus_Summon using its own public URL; WHEN running locally, a dev-only override MAY permit loopback hosts, but THE override SHALL be ignored when `NODE_ENV` is `production`.
